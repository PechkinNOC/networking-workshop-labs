## Рішення

**Причина:** та сама, що в demo - PMTUD blackhole. Відмінність: тут заблокований не тільки ICMP "fragmentation needed", а й ICMP echo-request (`ping`) - тому `ping` не є надійним індикатором взагалі, він мовчить незалежно від розміру пакета. Це і є пастка: перше враження - "це щось із firewall/зв'язністю в цілому", хоча насправді проблема виникає тільки для великих пакетів.

Знайти вузьке місце можна напряму, без `ping`:

```bash
ip -o link show
```

`cli0` (в бік клієнта) має MTU 1300, `srv0` (в бік сервера) - 1500. Ось і різниця, яку жоден з кінців сам не бачить.

**Рішення - те саме, що в demo:**

```bash
# Варіант 1 - прибрати блокування fragmentation-needed
iptables -D OUTPUT -p icmp --icmp-type fragmentation-needed -j DROP

# Варіант 2 - MSS clamping (працює навіть якщо ICMP і далі заблокований)
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

Зверни увагу: варіант 2 виправляє `curl`, **навіть якщо `ping` так і лишається заблокованим** - MSS clamping не залежить від ICMP взагалі.

**Ключовий висновок:** коли `ping` не відповідає, це не завжди означає "немає зв'язку". Він міг впертись у своє власне, окреме блокування. Перевіряй симптом тим інструментом, який дійсно відтворює скаргу (тут - `curl` з реальним обсягом даних), а не тільки базовим `ping`.
