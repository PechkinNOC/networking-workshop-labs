## Рішення

**Причина:** та сама, що в demo - асиметричний роутинг.

`ss -tlnp` показував `0.0.0.0:8080` - сервіс слухає на всіх інтерфейсах, це виглядало нормально.
Але відповідь виходила через основний інтерфейс: адреса, на якій слухає сервіс, не впливає на вибір маршруту.

**Рішення - те саме:**

```bash
ip route add 10.10.20.0/24 dev eth1 table 100
ip route add default via 10.10.20.100 dev eth1 table 100
ip rule add from 10.10.20.1 table 100
```

**Ключовий висновок:** `0.0.0.0` означає, що сервіс слухає, але відповідь іде за routing table.

### Ще простіший варіант

Замість policy routing можна обійтись одним рядком:

```bash
ip route add 10.10.30.0/24 dev eth1
```

Без `via` ядро вважає підмережу "on-link" і резолвить адресу клієнта напряму через ARP - у нашому стенді
це працює, бо клієнт і сервер сидять на одному L2-сегменті (veth-пара). У реальній мережі з окремим
роутером між сервером і клієнтом це не спрацювало б - там потрібен явний `via <next-hop>`.
