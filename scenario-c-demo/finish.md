## Рішення

**Причина:** PMTUD blackhole. Клієнт і сервер обидва мають нормальний MTU 1500 на своїх власних інтерфейсах - жоден із них не підозрює про вузьке місце. Але між ними, на самому роутері, один з інтерфейсів має MTU 1400. TCP MSS узгоджується на основі **власного локального** інтерфейса кожної сторони, тому обидва боки думають, що можуть слати сегменти по 1460 байт. Коли такий сегмент доходить до роутера і не влазить у вихідний інтерфейс (1400, DF-біт стоїть) - роутер має надіслати ICMP "Fragmentation Needed" назад відправнику, щоб той зменшив розмір. Але цей ICMP заблокований - типова "security hardening" помилка (хтось заблокував ICMP, думаючи, що це лише про `ping`). Відправник ніколи не дізнається і повторно шле той самий завеликий пакет - нескінченно.

Чому `ping` і `curl -I` при цьому працюють: обидва вкладаються в маленькі пакети, набагато менші за 1400 байт - вузьке місце їх не зачіпає. Проблема виникає тільки коли реальний обсяг даних перевищує поріг.

**Рішення - варіант 1 (корінна причина):**

```bash
iptables -D OUTPUT -p icmp --icmp-type fragmentation-needed -j DROP
```

Розблокувати ICMP - PMTUD знову працює, сервер сам дізнається про менший шлях і адаптується.

**Рішення - варіант 2 (надійніше):**

```bash
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

MSS clamping переписує MSS прямо в SYN-пакеті, що проходить через роутер, підлаштовуючи його під реальний вихідний MTU. Працює, навіть якщо ICMP заблокований десь на шляху, який ти не контролюєш (типова практика для VPN/тунельних шлюзів).

**Ключовий висновок:** `ping` і легкі health-check запити не гарантують, що реальний трафік проходить - вони можуть бути замалі, щоб зачепити проблему. Якщо моніторинг зелений, а справжні запити висять - перевіряй розмір пакетів, а не тільки факт з'єднання.

**Persistent:** MSS clamping зазвичай додають постійно на будь-якому VPN/тунельному інтерфейсі незалежно від того, чи є проблема прямо зараз - це стандартна практика, а не разовий фікс.
